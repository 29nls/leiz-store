# Phase 1: Order and Payment Integrity

## Status

Approved design; implementation pending.

## Goals

- Remove payment confirmation tokens from URLs.
- Add optional idempotency support to `POST /api/orders`.
- Prevent duplicate order creation and duplicate stock reservation on matching retries.
- Keep committed orders successful even if post-commit analytics or logging fails.
- Preserve existing payment confirmation security controls and backward compatibility during migration.
- Add focused unit, route, integration, and concurrency coverage.

## Scope

In scope:

- `src/app/checkout/page.tsx`
- `src/app/payment/[orderId]/page.tsx`
- `src/app/api/orders/route.ts`
- `src/app/api/orders/[orderId]/confirm/route.ts`
- Order/payment services, repositories, validators, and token utilities as needed
- Supabase schema/migration required for idempotency
- Related tests and deployment configuration/documentation needed by this phase

Out of scope for this phase:

- Unifying admin authentication
- Centralized admin pagination/search validation
- Broad accessibility redesign
- Durable event queue replacement for analytics/logging

## Architecture and data flow

### Order creation

1. The checkout page creates one UUID for each logical checkout submission flow.
2. It sends the UUID in the optional `Idempotency-Key` request header.
3. `POST /api/orders` validates the order body and validates the key when present.
4. The order service normalizes the request into a stable fingerprint, excluding the idempotency key itself.
5. The database boundary enforces uniqueness for the key and scope. A matching replay returns the original order; reuse with a different fingerprint is rejected.
6. The existing atomic order RPC remains authoritative for product prices, stock reservation, order items, and the payment-token hash.
7. On a newly created order, the API sets an order-scoped HttpOnly cookie containing the raw confirmation token.
8. The response contains the order but never contains `paymentConfirmationToken`.
9. The client navigates to `/payment/{orderId}` with no token query parameter.

Requests without an idempotency key remain supported for backward compatibility, but receive no duplicate-request guarantee.

### Confirmation token transport

The confirmation token is transported by a secure, order-scoped cookie:

- `HttpOnly`
- `Secure` in production
- `SameSite=Lax`
- `Path=/api/orders/{orderId}/confirm`
- `Max-Age` aligned with payment expiry

The confirmation endpoint reads the cookie and verifies it against the stored hash. During the compatibility window, a body token may be accepted for older clients. Query-string tokens are not accepted and are never generated by the application.

The implementation must avoid putting the raw token in logs, analytics payloads, error messages, or response JSON.

### Idempotency replay

Idempotency records must provide:

- A unique key boundary, scoped to the operation/client context.
- A normalized request fingerprint.
- A reference to the created order.
- State sufficient to distinguish an in-flight request from a completed replay.
- Timestamps and expiry/retention metadata.

The raw payment token must not be stored in plaintext. If a replay must recreate the confirmation cookie, the token is stored using authenticated encryption with a dedicated server secret. The encryption key is supplied through an environment variable and must fail clearly when a new order requiring replay support cannot safely use the feature.

Concurrent requests with the same key must be serialized by the database uniqueness boundary or an equivalent transactional claim. Application-level pre-checks are not sufficient.

A matching key with a different normalized payload returns a conflict response. The response must not reveal unrelated order data.

### Post-commit side effects

The atomic order result is considered committed once the database RPC succeeds. Analytics and order logging run afterward as best-effort side effects:

- Independent operations use `Promise.allSettled` or equivalent isolation.
- Failures are logged with order ID and operation name, without secrets or customer-sensitive payloads.
- Side-effect failures do not convert a successful order response into a 5xx response.
- The order response is returned from the committed order result.

A durable event queue may replace this best-effort approach in a later phase; it is not required for the initial change.

## API behavior

### `POST /api/orders`

- Accepts optional `Idempotency-Key` header.
- Validates key format and a bounded length when supplied.
- Returns `201` for a newly created order.
- Returns the same successful order representation for a matching completed replay.
- Returns `409` for a key reused with a different payload.
- Preserves the existing validation and error envelope.
- Does not expose the raw payment token in JSON.
- Sets the confirmation cookie for newly created orders and valid replays when the token can be safely recovered.

The exact replay status code may remain `201` for compatibility if the response envelope does not distinguish replay; tests must assert stable semantics rather than relying on an undocumented status difference.

### `POST /api/orders/{orderId}/confirm`

- Reads the scoped cookie first.
- May accept a body token temporarily for old clients.
- Ignores or rejects query-string token input.
- Retains rate limiting, token hash verification, duplicate-confirmation protection, proof validation, and legal status transitions.
- Returns the existing safe error envelope without exposing token or order-existence details unnecessarily.

## Error handling

- Malformed idempotency keys: validation error.
- Same key with a different request fingerprint: conflict.
- In-flight duplicate: return a safe retry response or the committed result once available; never create a second order.
- Database uniqueness races: resolve by reloading the idempotency record/order and applying the fingerprint check.
- Missing encryption key where encrypted replay storage is required: fail closed for the idempotency path and emit an actionable server-side configuration error.
- Analytics/logging failure after commit: warning/error telemetry only; checkout remains successful.
- Confirmation token failure: generic invalid/expired confirmation response.

## Testing plan

### Unit tests

- Stable request fingerprinting.
- Idempotency-key validation and conflict detection.
- Authenticated token encryption/decryption and tamper rejection.
- Side-effect failure isolation.

### Order/API tests

- New keyed order sets the scoped HttpOnly cookie.
- Order JSON does not contain the raw token.
- Matching keyed replay returns the original order.
- Same key with changed payload returns conflict.
- Missing key remains compatible.
- Analytics failure does not fail a committed order.
- Logging failure does not fail a committed order.

### Payment/route tests

- Payment URL has no `token` query parameter.
- Confirmation succeeds with the cookie.
- Temporary body-token compatibility works if retained.
- Query-string token is rejected or ignored.
- Invalid, expired, duplicate, and rate-limited confirmations behave safely.
- Payment-proof upload remains functional.

### Concurrency/integration tests

- Concurrent requests with the same key create one order and one stock reservation.
- Concurrent requests with different keys still obey stock constraints.
- Database uniqueness and replay behavior are tested against the Supabase migration/RPC boundary where integration infrastructure is available.

## Operational requirements

- Add and document the idempotency/encryption environment variable(s).
- Add the idempotency migration before deploying application code that depends on the table/constraint.
- Ensure cookie behavior is tested under HTTPS production settings and local HTTP development settings.
- Do not overwrite unrelated working-tree changes in CI, Docker, or lockfiles.

## Acceptance criteria

- No application-generated payment URL contains a raw confirmation token.
- A client retry with the same idempotency key cannot create a second order or reserve stock twice.
- A changed payload using an existing key is rejected.
- A successful atomic order is returned successfully even when analytics or logging fails afterward.
- Existing payment confirmation protections continue to pass.
- Focused tests cover all behaviors above.
- Typecheck, lint, unit tests, build, and relevant E2E tests pass in an environment with dependencies installed.
